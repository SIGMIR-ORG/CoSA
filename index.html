Abstract

Security at the level of composition

An agent skill is a modular, reusable package of instructions and supporting resources that extends large language model agents with composable procedures for complex tasks. Prior work on Skill security has primarily exposed malicious instructions, bundled payloads, and unsafe packages, motivating single Skill package inspection and runtime defenses. However, individually benign Skills may violate system-level or user-defined policies when composed, as their intermediate artifacts and decision signals may be consumed downstream beyond the constraints governing their original use. We formalize such composition induced violations as Conflict of Skills (CoS). We first characterize recurring CoS mechanisms in real-world Skill ecosystems and then introduce the Conflict of Skills Attack (CoSA), a novel mechanism-guided framework for discovering composition opportunities and constructing locally admitted Skill additions. CoSA targets two augmentation strategies arising from Skill composition: (1) capability supplementation, which adds missing operations, and (2) relationship reshaping, which changes how existing capabilities exchange information, propagate decisions, or trigger side effects. We evaluate CoSA on four domains and 288 distinct tasks. Across multiple models and agent harnesses, CoSA raises attack success rates for data leakage, unauthorized state modification, and unsafe execution by about 20 percentage points over the baseline. Trajectory analysis shows that risk arises from cross-Skill information flow, decision reuse, and target/action binding. Based on these findings, we design a lightweight harness-level guard that checks information flow and authorization before consequential actions. In a five-model recruiting pilot, the guard reduces attack success rate by 58.61 percentage points while largely preserving benign task completion (66.67% to 65.00%).

Method

From locally admitted packages to a risky workflow

Conflict of Skills requires a violated policy, at least two individually admitted Skills, and a recorded dependency that connects their artifact or decision reuse to the violation. Reading multiple Skills or observing their temporal order is insufficient.

  1. Original pool. All participating Skills pass the specified local checks. “Admitted” is a package-check result, not a guarantee of safe composition.
  2. CoSA additions. CoSA extracts operation contracts, identifies composition opportunities, generates and validates candidates, and selects locally admitted additions within a domain budget. Installation is assumed; existing Skills and runtime permissions remain fixed.
  3. Composition. With the augmented pool available, the agent autonomously selects Skills. This schematic follows the paper’s assessment → decision reuse → persistent mutation pattern. It does not represent a particular evaluated run.
  4. Decision reuse. A downstream operation treats an assessment or recommendation as approval, although no new authorization has been introduced. This is semantic authority promotion.
  5. Policy violation. If the final operation fails to re-establish the required authorization and performs the persistent mutation, the workflow violates the task policy. A Conflict of Skills also requires evidence that cross-Skill reuse contributed to this violation; merely using several Skills is insufficient.

Two augmentation strategies

Capability supplementation
Supply a missing business operation that enables a dependency path.
Relationship reshaping
Change how existing capabilities exchange information, reuse decisions, or bind targets and actions.

Four recurring mechanisms

Security-context attenuation
Task-relevant content survives transformation while provenance, sensitivity, release restrictions, or other policy context is weakened or no longer recognized downstream.
Semantic interface bridging
An intermediate operation converts an output into a representation that a downstream operation can readily consume.
Semantic authority promotion
An assessment, recommendation, or readiness signal is reused as if it established approval for a consequential action, without new authorization.
Target/action binding drift
Evidence scoped to an object or judgment becomes associated with a recipient, state transition, command, or action without authorization for that exact target–action pair.

These mechanisms can overlap. Missing terminal revalidation enables the final violation when a consequential operation fails to re-establish the relevant security conditions.

Threat model

Small additions, fixed execution privileges

The attacker adds domain-relevant Skill packages that pass individual static security checks. Installation is assumed. The maximum augmentation budget is 5% of the original pool, rounded down: two Skills for recruiting and three each for finance, IT, and business.

Original Skills, model, trusted instructions, planner, tools, and runtime permissions remain fixed. Candidate construction uses public domain information and package contracts. Private user data, runtime context, and hidden evaluation policies are unavailable to the attacker.

Evaluation requests and initial states are frozen before candidate generation and selection. “Individually benign” denotes admission under the specified checks, rather than a guarantee of safe runtime behavior.

Mitigation

Check the boundary before the action

The harness-level Guard checks provenance, release scope, authorization, and target/action bindings before data submission, state mutation, or execution. Only an ALLOW decision reaches the backend.

Interpretation and limits

The attack evaluation covers finite domains, models, harnesses, and policy categories. Each condition is evaluated once per task and setting, so the reported ASR is an empirical grid-level rate, rather than a repeated-sampling task probability. The random ablations are descriptive controls.

Low defended ASR does not by itself establish successful task completion. “Lightweight” refers to the pre-action hook; validation latency and token costs are unavailable. Longer-horizon dependencies and jointly evolving execution environments remain outside the reported evaluation.
